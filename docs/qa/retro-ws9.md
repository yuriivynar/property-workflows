# Ретро WS9: що б ми взяли з фабрики у свій звичайний процес

Зріз 3 («вендор — виконавець задач», AC-VENDOR-01…10) зроблено звичайним способом: специфікація → план → задачі окремими PR →
ворота й CodeRabbit → злиття → `db-deploy`. Станції фабрики на занятті — допуск, захищені тести, приховані сценарії,
мутації й повтор, рев'ю-спростування, пакет доказів із «Не перевірено», рівні автономії, бюджети. Нижче — по станції:
«уже є», «візьмемо» (з конкретним файлом чи налаштуванням) або «не потрібно, бо …». Бонус із самою фабрикою не робили,
тож це міркування з прикладів на занятті, а не з власного прогону.

- **Допуск (чи задача готова до роботи) — візьмемо:** пункт `tasks.md` не починаємо, доки в ньому немає трьох рядків —
  «Done when: AC-…», «Рівень тесту» і «Доказ відмови (мутант чи червоний прогін)». Де: шаблон пункту в
  `openspec/changes/impl-<зріз>/tasks.md` (зараз лише «Done when») і рядок у чеклісті `.github/pull_request_template.md`.
- **Захищені тести — візьмемо:** тест пишемо першим окремим комітом PR (червоний), реалізацію — наступним, а в описі PR
  стоїть SHA червоного коміту. Де: чекліст `.github/pull_request_template.md`. Уже є половина: тести з AC ID в назві
  (`npm run ac:coverage` ловить ORPHAN і MISSING). Заборону змінювати тести разом із кодом без пояснення не беремо:
  одна людина, тож правило виконувала б сама ж людина.
- **Приховані сценарії — не потрібно, бо** ми не віддаємо виконання машині: їх призначення — не дати агентові
  підігнати код під видимі тести. У нашому процесі роль «прихованого» грають UAT на проді (`docs/qa/uat/`, сценарії пишуться
  з тексту AC, а не з коду) і приймання PM.
- **Мутації й повтор — візьмемо:** SQL-мутанти для кожного правила відмови в міграціях — тепер це окремі записи V02–V09 у
  `scripts/mutants.mjs` (усі KILLED, `npm run mutation:sql`); додати їхній запуск до `.github/workflows/quality.yml` як
  необов'язкову перевірку PR, що змінює `supabase/migrations/**` (зараз мутанти запускаємо руками). Повтор «упав → виправ → ще
  раз» лишається за людиною.
- **Рев'ю-спростування — уже є:** CodeRabbit (`.coderabbit.yaml`, `@coderabbitai review` у шаблоні PR) і правило «на
  кожну знахідку — виправлення або аргумент у треді». Візьмемо тільки форму: таблицю відповідей на знахідки в описі PR
  (WS8 P15), щоб PM бачив її одним поглядом.
- **Пакет доказів із «Не перевірено» — уже є:** `docs/qa/proof-pack.md` (рядок на AC, розділ «Не перевірено» з причиною),
  попередній — `docs/qa/proof-pack-ws8.md`. Візьмемо: рядок proof pack заповнювати в тому самому PR, що й тест, а не після UAT
  (зараз — окремим PR наприкінці), інакше посилання на SHA доводиться закріплювати повторно.
- **Рівні автономії — уже є:** `AGENTS.md` («Завжди / Спитай спершу / Ніколи»), ruleset `solo-main` (злиття лише через PR із
  зеленими `spec`, `app`, `conformance`, `db-check`). Візьмемо: дозвіл на push і PR фіксувати в `AGENTS.md` на тиждень, а не
  переказувати в чаті.
- **Бюджети — візьмемо:** до пункту `tasks.md` додаємо поле «Бюджет, год» і в описі PR — фактичне, а підсумок тижня
  порівнюємо з планом із walkthrough (14–18 год). Де: `openspec/changes/impl-<зріз>/tasks.md`, розділ «Що змінилось» у
  `.github/pull_request_template.md`. Те саме для токенів моделі: рядок у proof pack, розділ C «Рецензент».
- **Урок із цього зрізу:** правило відмови для вендора живе в базі (RLS і `security definer`-функції), тому доказом
  служать тести PGlite й SQL-мутанти, а не мок `rpc` чи інтерфейс; e2e показує лише «що видно» й «що не змінилося».
