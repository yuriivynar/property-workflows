## Підсумок

Навчальний дріл: для гілки `staging` у Vercel додали перевизначення `NEXT_PUBLIC_SUPABASE_URL` з одним зміненим
символом у ref і перезібрали staging. Через 20 секунд після того, як деплой став Ready, smoke деплою почервонів і
надіслав алерт у Telegram. Розбір агентом у профілі «лише пропонує» знайшов причину за доказом у `/api/health`;
людина прибрала перевизначення й перезібрала staging. Збій тривав 48 хвилин 54 секунди (від Ready зламаного деплою до
зеленого smoke).

## Вплив (мовою користувача)

- Протягом ~49 хвилин на staging (тестова копія застосунку) сторінка входу відкривалась, але увійти й побачити
  шаблони, запуски чи задачі було неможливо: застосунок не діставався до своєї бази.
- Цієї години на staging ніхто не тестував (дріл оголошено в чаті команди заздалегідь), тож реально не постраждав
  ніхто.
- Прод, база проду й дані клієнта не зачеплені. Дані staging не втрачено й не змінено.

## Виявлення

- **Сигнал:** червоний smoke job `deploy` за подією Vercel `repository_dispatch` → алерт у Telegram.
- **Час до виявлення:** від Ready зламаного деплою (14:50:31) до алерту (14:50:51) = **20 секунд**. Передбачено в #117 —
  ≤ 5 хв.
- **Час до відновлення:** від алерту (14:50:51) до зеленого smoke (15:39:25) = **48 хв 34 с**; з них розбір агентом —
  21 хв, виправлення й перезбірка — ~2 хв, решта — очікування початку розбору.
- Без сигналу: зламаний staging помітив би лише той, хто відкрив його для тестування (PM на UAT) — найпевніше, годинами
  пізніше.

## Першопричина

| Твердження | Доказ |
|---|---|
| Деплой staging збирався з адресою бази, ref якої відрізнявся від проєкту staging на один символ | `/api/health` у червоному прогоні: `"supabaseRef":"ukbnybazjlbicejpfjvx"`; у нормі й після виправлення — `"ukbnybazjlbicejpfjvz"` (прогони 45198547199, 45195373615, 45207624385) |
| `supabaseRef` береться саме з `NEXT_PUBLIC_SUPABASE_URL`, тож хибною була ця змінна | `src/app/api/health/route.ts` (`supabaseRefFrom(process.env.NEXT_PUBLIC_SUPABASE_URL)`), коміт `b61d52c` |
| За такою адресою база не відповідає: запит падає на рівні мережі, а не з відмовою бази | `reason: "status-0"` — `src/lib/health.ts`: статус 0 = мережа |
| Код не змінювався: зламаний і робочий деплої зібрано з того самого коміту | `"sha":"b61d52c…"` в обох прогонах |

**Тригер:** нове перевизначення змінної `NEXT_PUBLIC_SUPABASE_URL` лише для гілки `staging` + Redeploy (значення
`NEXT_PUBLIC_*` вбудовуються під час збірки). Перевірки значення до збірки немає: Vercel приймає будь-який рядок.

## Що НЕ було причиною

| Гіпотеза | Як перевірили | Чому відкинули |
|---|---|---|
| Зміна коду / регресія | SHA у health зламаного й робочого деплою | обидва `b61d52c`, нового коміту між ними немає |
| Міграція чи схема бази staging | Actions → CI; дріл без міграцій | останній `db-deploy-staging` — 12:19 UTC, до зеленого smoke о 14:32 |
| База staging на паузі | `reason` у health | було б `paused`; після виправлення база відповіла одразу, без Resume project |
| Хибний publishable key | `reason` у health | було б `invalid-api-key` (як у справжньому збої того ж дня, 13:20 UTC, прогін 45182996655) |
| Захист Vercel чи секрет обходу | журнал smoke | `"bypass":true`, `/` → 307, `/login` → 200: сторінки відкрились |
| Інцидент провайдера (Supabase, Vercel) | smoke проду о 14:50:33 (прогін 45198540050); staging після виправлення | прод-база відповідала; staging запрацював, щойно повернули правильну адресу, без змін у провайдера. Статус-сторінки не перевіряли — «невідомо», але час і механізм пояснено повністю |

## Усунення

- **Зупинили шкоду:** людина прибрала лише додане перевизначення `NEXT_PUBLIC_SUPABASE_URL` для гілки `staging`
  (`APP_ENV` і загальні змінні Preview не чіпали) → Redeploy → smoke зелений. Instant Rollback для staging недоступний
  (лише прод), а Redeploy старого деплою зібрався б з тими самими хибними змінними — це правильно відзначив агент.
- **Виправили причину:** перевірка, яка ловить невідповідність бази до того, як шукати «чи впав Supabase», — #119
  («Дії», дія 1).

## Що спрацювало, що ні, де пощастило

- **Спрацювало:**
  - алерт за 20 секунд після Ready — з середовищем, гілкою, адресою деплою й посиланням на прогін;
  - поле `supabaseRef` у health (додане цього ж тижня) дало прямий доказ причини без доступу до значень змінних;
  - профіль «лише пропонує»: читання значення змінної впиралось у `ask`, відкат — у `deny`; агент нічого не змінив;
  - агент сам вказав, що Redeploy старого деплою не допоможе.
- **Не спрацювало:**
  - підказка smoke розмита: «Supabase недоступний чи `NEXT_PUBLIC_SUPABASE_URL` у Vercel не той?» — черговий мав
    сам порівняти ref з очікуваним;
  - MCP Vercel відповідав 403 / 404 на деплої й журнали: агент не прочитав журнали Vercel (на Hobby вони живуть
    1 год) і брав дані з GitHub; Vercel CLI для запасного шляху (`vercel logs`) не встановлено;
  - асистент чергового не написав чернетку: ключа моделі ще не було;
  - між алертом і початком розбору минуло 22 хв — у реальному інциденті це час, коли журнали Vercel ще живі, але
    спливають.
- **Пощастило:** це був staging у навчальний час, ніхто не тестував; у проду той самий тип помилки (хибна змінна
  Production) зупинив би всіх користувачів.
