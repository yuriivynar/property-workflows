# 0003. Права перевіряє кожна дія (getClaims + роль з profiles) і база (RLS, GRANT, функції), без admin-клієнта

- Статус: прийнято
- Дата: 2026-10-26
- AC: AC-EDITOR-07, AC-EDITOR-08, AC-EDITOR-09, AC-DSYS-02, AC-DSYS-03

## Контекст

Матриця прав PM (`requirements/product.md`): шаблони створює, змінює й зберігає як версію лише адміністратор; список
версій — лише адміністратор; відвідувач без входу бачить лише сторінку входу. Відмовні AC вимагають, щоб менеджер не
змінив шаблон **навіть прямим запитом, оминаючи сторінки** (AC-EDITOR-08). Server Action — публічний POST-ендпойнт, а
публічний ключ Supabase лежить у JS-бандлі: будь-хто може викликати дію напряму або надіслати запит прямо в базу.
`src/proxy.ts` лише перенаправляє на `/login` — це UX. Роль зберігається в `profiles.role` (ADR зрізу 1, міграція ролей).

## Рішення

Дві лінії захисту, обидві обов'язкові:

1. **Дія.** Кожна server action першим кроком викликає `requireAdmin()` / `currentUser()`
   (`src/lib/auth/require-role.ts`): `getClaims()` (перевіряє підпис JWT) → роль з `public.profiles` за `claims.sub`
   (ніколи з `user_metadata`) → не та роль — відмова **до** будь-якого запису. Сторінки редактора й списку версій для
   менеджера навіть не запитують даних — показують «Not enough rights».
2. **База.** Запис — **клієнтом користувача**: діють RLS (окрема політика на select / insert / update / delete) і
   колонкові GRANT; привілейовані дії (`save_template_version`, `move_template_item`, `launch_run`) — функції в
   `private` (`security definer`, `set search_path = ''`, роль першим рядком) з тонкими обгортками `security invoker`
   у `public`; `anon` не має прав на жодну таблицю шаблонів і запусків.

Admin-клієнт (`SUPABASE_SECRET_KEY`) у застосунку не використовуємо й у Vercel не додаємо: у зрізі немає Admin API.

## Розглянуті варіанти

- **Лише RLS, без перевірки в дії** — чому ні: дія відпрацює до кінця й покаже загальну помилку замість «Not enough
  rights»; частина записів (наприклад, кілька `update` поспіль) може пройти частково, якщо одну з політик колись
  послаблять; перевірка в дії дає ранню відмову й зрозумілий текст з AC.
- **Лише перевірка в дії + admin-клієнт для запису** — чому ні: admin-клієнт обходить RLS, тож одна забута перевірка в
  новій дії (або прямий запит до бази з публічним ключем) відкриває запис усім; секретний ключ довелося б тримати у
  Vercel. Саме так виникла CVE-2025-48757.
- **Роль у JWT (Custom Access Token Hook) замість `profiles`** — чому ні: зміна ролі діє лише після оновлення токена;
  потрібен ще один хук і його тест; для двох ролей і навчального обсягу перевага не варта складності.

## Наслідки

- Простіше: кожен відмовний AC має тест на рівні бази (PGlite, `asUser` / `asAnon`) і на рівні дії (моки) — правило
  видно в коді й у тестах.
- Складніше: кожна нова дія мусить викликати перевірку — це охороняє правило в CI (нижче), а не пам'ять розробника.
